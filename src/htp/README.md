# Qwen2VL Hexagon HTP preprocessing

`GENIEXPROC_ENABLE_HTP` is OFF by default and currently requires Windows ARM64, the Hexagon SDK (`HEXAGON_SDK_ROOT`, `HEXAGON_TOOLS_ROOT`), a matching FastRPC runtime, and signed v73/v81 DSP skels on the device. The host build creates DSP skels and, when `GENIEXPROC_HTP_CERT` (or `HEXAGON_HTP_CERT`) is set, signs the catalog. After building, install the payload independently with `cmake --install build --prefix <prefix> --component geniex-proc-htp`; this works with `GENIEXPROC_INSTALL=OFF`. The component requires both v73/v81 skels, installs them under `bin/geniex-proc-htp`, includes the generated `.cat` and `.inf` when signing is configured, and optionally installs `GENIEXPROC_HTP_CDSPRPC_DLL` as `libcdsprpc.dll`. An unsigned install clears the installed proc catalog and INF; when HTP is disabled, the same explicit component removes the proc HTP payload directory. This is a neutral payload location, not a QAIRT runtime destination; the consuming SDK/plugin owns final runtime staging. Only Qwen2VL selects this backend via `Qwen2VLConfig::preprocess_device = PreprocessDevice::NPU` or `GENIEX_QAIRT_PREPROCESS_DEVICE=npu` before process launch; other processors and the default CPU path are unchanged. Absence of a working HTP is an error, not a CPU fallback.

With an unmodified geniex SDK, a QAIRT runtime override (`GENIEX_QAIRT_LIB` or `--qairt-lib`) replaces `ADSP_LIBRARY_PATH`. For HTP preprocessing, either use the bundled runtime without an override or install the signed proc skel into a directory in the final QAIRT DSP search path; exporting an additional path alone will not survive that override. On Windows, `geniex-proc-vision.dll` imports `libcdsprpc.dll` even when CPU/GPU preprocessing is selected in an HTP-enabled build. The SDK plugin loader uses `LOAD_LIBRARY_SEARCH_*` flags, so `PATH` alone may not find it: make a compatible installed FastRPC host DLL discoverable in the plugin directory or via `AddDllDirectory`. On QCS, the `qcnspmcdm8380` DriverStore variant worked; `qcadsprpc8380` returned AEEResult `0x72` when querying the DSP architecture.

The decoded RGB image starts in host memory. One synchronous FastRPC call resizes it with Catmull-Rom, then normalizes and extracts Qwen2VL patches on the DSP using the **configured** scale, mean, and standard deviation. The RPC returns host-float patches for `BatchFeatures` and QNN input; the image input and patch output still cross the host/DSP boundary, so this is not zero-copy preprocessing. See [`PERF.md`](../../PERF.md) for the recorded measurements and their limitations; they do not establish an end-to-end speedup for HTP.

The RPC, v73/v81 skel, signing and session implementation is adapted from the `feat/htp-backend` branch of `qualcomm/geniex-proc` (commit `21e06b9f82e9b660a15c855d4955be3d2debd259`). Run `qwen2vl_device` with `GENIEXPROC_BUILD_TESTS=ON` on a configured qcs machine to verify real HTP output against CPU (up/down/identity resize, custom normalization and multi-image patch ordering). A signed skel/catalog alone is not proof of a security-validated DSP chain; validate the device's installed driver and policy separately.
